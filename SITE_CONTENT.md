## 7. System thesis and local-first benefits

### System thesis

The site separates reasoning from execution: cloud models make difficult
decisions while local models handle code, retrieval, embeddings, and drafting.
The two nodes are deliberately independent so either can be rebuilt without
bringing down the whole system. Programs share the same router, policy
boundary, and local-first default.

### Local-first benefits

| Benefit | Site position |
| --- | --- |
| Data sovereignty | Content stays on the network |
| No metering | Bulk generation, embeddings, and long agent loops have no per-token local cost |
| Low latency | Models run beside the data rather than behind a distant public API |
| Offline resilience | The lab continues when connectivity is unavailable |
| Reproducibility | Services rebuild from repositories instead of hidden state |
| Enforced boundary | An audited gate controls what may reach the cloud |

## 9. Routing layer

The routing section presents a four-stage sequence:

1. **Classify** — `intercept.py` evaluates the pending tool call against the
   tier map.
2. **Route** — reasoning/review goes to the cloud brain, heavyweight generation
   may use the cloud coder, and volume execution goes to local Gemma 4 models.
3. **Enforce** — a FastMCP stdio tier enforcer applies the boundary across a
   six-layer harness.
4. **Return** — the cloud reasoning layer receives only material that needs a
   decision.

Displayed labels include “Claude Tier System · v10.1,” “six-layer harness,” and
“production-grade · local-first.”

## 11. dsr-OMS

### Product position

dsr-OMS is presented as one canonical operational workflow across marketplaces,
ONDC, brand webstore, stores, and warehouses. It covers orders, shipments,
routing, inventory, locations, integrations, AI insights, and audit history.

The deterministic transactional core reserves stock, minimises shipment splits,
selects eligible fulfilment locations, applies a four-hour allocation-acceptance
SLA, and releases stock before atomic rerouting.

### Current release boundary

The public status is **working local MVP**, not a certified production rollout.
The implemented local application, APIs, transactional workflows, and automated
tests are distinguished from remaining live-provider requirements:

- tenant credentials and mappings;
- provider sandbox certification;
- enterprise identity;
- managed infrastructure;
- business UAT.

Displayed release indicators are:

- four-hour allocation-acceptance SLA;
- eight seeded channel templates;
- HMAC-signed webhook intake;
- read-only AI operations boundary.

### Order lifecycle

1. Ingest — idempotent channel order intake.
2. Reserve — sellable and safety stock.
3. Route — zone, distance, and priority scoring.
4. Accept — four-hour SLA or atomic reroute.
5. Fulfil — invoice, AWB, pick, and pack.
6. Dispatch — manifest and stock commitment.
7. Resolve — return, QC, refund, and reconciliation.

### Capabilities

- Unified order workspace
- Deterministic smart routing
- Fulfilment lifecycle controls
- Returns, item-level QC, restock, and refunds
- Signed/idempotent webhooks and transactional Ginesys outbox
- Governed master data, integrations, RBAC, and platform administration

### AI boundary

The AI copilot is advisory and cannot accept, cancel, reroute, reserve stock,
issue refunds, or update ERP state. Deterministic services remain authoritative.
The copilot reads masked operational snapshots, returns structured advice,
supports approved local or opt-in cloud providers, flags risk for human review,
falls back to deterministic summaries, and audits operational metadata without
recording full prompts or customer PII.

The section links to the
[`DSR-OMS` repository](https://github.com/dineshsrivastava07-cell/DSR-OMS).

## 12. Research, build, security, and resilience

### Research, test, and build

The site describes local models as the low-cost sandbox for large agent loops,
evaluation, adversarial testing, and iteration. MCP is presented as the common
socket through which tools, datasets, and knowledge vaults connect to agents.

### Security and resilience

- Default-closed data boundary.
- Explicit cloud escalation rather than silent model-selected escalation.
- OAuth authentication without API keys written to disk.
- Private WireGuard mesh behind a Cloudflare Tunnel.
- Nodes are not directly published to the internet.
- Independent node failure domains.
- Repository-based recovery and reproducible services.

The closing reach statement says the environment is reached through the
WireGuard mesh and Cloudflare Tunnel and published at `dsrailab.com`.

## 17. Update and verification workflow

For every website update:

1. Fetch `origin` and confirm the local branch is based on current `main`.
2. Update the relevant site source or asset.
3. Update this document in the same commit.
4. Check `git diff` and run `git diff --check`.
5. Parse the HTML and confirm required new or changed content is present.
6. Preview locally and verify desktop and phone-width layouts.
7. Check for horizontal overflow, missing assets, and browser console errors.
8. Commit and push to `main`.
9. Wait for the GitHub Pages workflow to complete successfully.
10. Fetch the live HTTPS page and confirm it matches the committed source.
11. Verify the live page in a fresh browser session.
